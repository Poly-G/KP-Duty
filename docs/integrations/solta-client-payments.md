# Solta client payment requests

KP administrators open a connected Solta delivery project and use Client payments. A request has a fixed USD amount, title, mode and durable UUID. Staff explicitly confirm it; the request appears in the authenticated client portal. No invoice or email is created. There are no automatic delivery or launch approvals. Test requests and receipts are clearly labeled and excluded from the real-money due total.

KP prepares the ledger row, then makes a bounded, purpose-signed POST to Solta /api/integrations/kp/billing to create the matching request. Successful publication updates KP. Interrupted requests retain their UUID and can be recovered with Retry publishing after reload. Amounts and identities cannot change on retry. Unused requests can be cancelled; checkout reservation locks the record and prevents cancellation once checkout has started. Stripe session creation keeps the existing stable idempotency key and 23-hour ambiguity guard.

The live portal webhook and existing sandbox /api/stripe/test-webhook verify signatures and strict live/test mode, session ID, paid status, request amount/currency and stored session identity. A payment, audit and outbox event are recorded atomically. Solta sends the event to KP /api/integrations/solta/payments using a separate path-bound billing signature. KP service-only RPC checks the exact prepared company/project/request, amount/mode and Stripe identities; duplicate receipts and conflicting payments fail. Failed dispatch retains the outbox event and makes Stripe retry its webhook. KP Refresh status also reconciles persisted paid records. This is payment status, not a refund or chargeback reconciliation system.

Receipt links require client/project authorization. Solta retrieves the exact succeeded PaymentIntent and latest paid Charge in the correct mode, validates amounts/currency and redirects only to HTTPS pay.stripe.com. Stripe handles receipt rendering and expired links. No invoices are enabled.

Configuration: existing shared bridge secrets and KP integration database key are reused server-side. STRIPE_SECRET_KEY must be live-prefixed for live requests. Scoped test requests use a separate STRIPE_PORTAL_TEST_SECRET_KEY (or an already test-prefixed key on Preview); no test flow can fall back to a live key. The existing STRIPE_TEST_WEBHOOK_SECRET validates the sandbox endpoint. New Solta portal_billing_control defaults enabled=false, live_enabled=false, test_projects=[]. Activation must start with the synthetic QA project before any live request.

Validation: 25 Solta backend tests including five new billing tests; 24 KP billing database checks; scoped lint and both production builds pass.
