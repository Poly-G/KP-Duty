# Deliverable version reviews

Solta and Sent delivery projects retain immutable deliverable versions. Each version has a description and up to 20 exact uploaded file versions from the same project. A related intake requirement is an informational link; attaching a file does not accept a requirement. Drive links remain available in project files, but approval attachments require a fixed uploaded export because Drive contents can change outside KP.

Active staff prepare versions. The assigned reviewer or an active administrator records internal approval or requested changes. Administrators can assign any active teammate as reviewer; other staff use the project owner. An explicitly published version must be the current version and internally approved. Publication shares its exact attachments and queues one held notification. Approval never starts delivery, confirms payment, launches a website or completes a project.

Staff can record an actual client response to a published current version, naming the client and retaining internal evidence. This is a staff record from email or a meeting, not a client-authenticated portal signature. Client feedback is visible in the preview; internal reviews, reviewer assignments and evidence are excluded. Direct client actions require the later authentication slice.

Each review lane allows one final response per version. Changes require a new version and fresh reviews. Older publications remain visible while a newer draft is private. Old reviews never approve a new version. Stale writes and new reviews of superseded versions are rejected; exact request retries retain their original receipt.

Company backup includes deliverable metadata, versions, file links, reviews and publications. Uploaded bytes still require a separate storage export. Both business practice pages exercise version changes, internal review, explicit publication and evidenced client responses without changing company records or sending email.

## Release batching

During the current build, `vercel.json` disables automatic Git deployments at the user's request. Render remains the testing deployment. When the Vercel allowance resets and the accumulated release is verified, restore automatic deployments or deploy the reviewed commit explicitly. Do not infer reset time from this configuration or silently leave daily production deployments disabled after the cutover.
