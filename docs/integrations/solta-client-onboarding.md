# Solta client onboarding from KP

Administrators open a Solta client delivery project and use Client portal access. Existing company/project creation stays in KP. Add one final approver and up to nine other people; confirm company-wide access. Replacing an approver requires explicit confirmation and affects all company projects. Existing members remain. Welcome emails are separate per-person actions after setup, use the branded sign-in button, and require normal client sign-in.

Setup uses durable request IDs: KP prepares a disabled mapping; Solta stages an inactive project; KP enables the exact mapping and project Drive storage; Solta atomically grants memberships and opens the project; KP records completion. Retries preserve mapping IDs and reject changed identities, payloads, disabled accounts, membership races, and revoked completed mappings. Delivery start and launch gates are unchanged.

The server-only signed POST /api/integrations/kp/onboarding derives a purpose key from the existing KP/Solta shared secret. Five-minute timestamp, one-use nonce, bounded payload, and company/project identity checks are required. KP Preview cannot provision Production. Solta portal_kp_onboarding_control defaults closed; activation may allow exact project IDs first, or all projects after release approval. No customer can call KP admin actions directly.
